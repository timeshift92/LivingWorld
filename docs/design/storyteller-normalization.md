# Living World — Нормализация интеграции: свой сторителлер вместо патчей

Статус: **глубокий анализ, направление к согласованию.** Отвечает на вопрос
«как нормализовать всю интеграцию с RimWorld»: увести генерацию событий с
Harmony-патчей ванильных `IncidentWorker` на **свои `IncidentDef` +
`IncidentWorker` + `StorytellerComp`**, свести inbound-sync к одному слою на
устойчивой идентичности, и убрать горячие патчи.

Связано: [gap-analysis.md §3](gap-analysis.md) (кастомный сторителлер — точка
интеграции; приоритеты #1, #2), [population-flow.md §5, §11](population-flow.md)
(материализация через ванильные инциденты; динамику держим в ledger'е),
[simulation.md](../simulation.md) (жизненный цикл рейда),
[специи шага 5](../superpowers/specs/2026-07-07-drifter-flow-materialization-design.md)
(Part B этого шага — postfix на `WandererJoin` — **этим анализом заменяется** на
свой инцидент; см. §10).

## 1. Диагноз: почему текущая интеграция «денормализована»

Сейчас интеграция — россыпь из **9 Harmony-патчей** без единой оси. Они смешивают
три разные обязанности (генерация, sync, UI) и используют **ненадёжную привязку по
`thingIDNumber`**, которую GC/RuntimeGC протухляет (gap-analysis §1 «WorldPawns-блоат»,
§2.A).

| Патч (цель) | Обязанность | Класс | Проблема |
|---|---|---|---|
| `IncidentWorker_RaidEnemy.TryResolveRaidFaction` | генерация рейда | **outbound** | патчим ванильную генерацию; конфликт с Rim War и др. патчерами (§D) |
| `IncidentWorker_Raid.TryGenerateRaidInfo` | генерация рейда | **outbound** | то же; логика размазана по двум точкам ванили |
| *(планируемый)* `IncidentWorker_WandererJoin` (Part B шага 5) | материализация притока | **outbound** | ещё один postfix на ванильную генерацию; частоту не контролируем |
| `Pawn.Kill` | смерть → ledger | **inbound** | привязка по `thingIDNumber` |
| `Pawn.ExitMap` | возврат/пропажа → ledger | **inbound** | привязка по `thingIDNumber` |
| `Pawn.DeSpawn` | возврат/пропажа → ledger | **inbound** | **горячий путь** — каждый деспавн (gap-analysis §3 прямо критикует) |
| `Pawn_GuestTracker.CapturedBy` | плен → ledger | **inbound** | привязка по `thingIDNumber`; нет обратного sync вербовки/эмансипации (§2.A) |
| `Settlement.GetInspectString` | UI | *read-only* | безобиден, оставляем |
| `Dialog_Trade.Close` | экономика | *hook* | безобиден по частоте (на сделку), оставляем |
| `Page_CreateWorldParams.DoWindowContents` | worldgen UI | *UI* | безобиден, оставляем |

**Три системных изъяна:**

1. **Генерация патчит ваниль.** Каждый outbound-патч воюет за один и тот же метод
   ванильной генерации, где уже сидят другие моды (Rim War — приоритет №1 по
   совместимости, §D). Это «двойное вождение» фракций и хрупкость.
2. **Нет спинного хребта идентичности.** И outbound, и inbound опираются на
   `thingIDNumber`, который **не переживает GC/переспавн** (§2.A, §1). Ledger
   объявлен источником истины, но связь с материализованной пешкой рвётся.
3. **Горячие пути.** `Pawn.DeSpawn` дёргается на каждый деспавн; логика населения
   должна жить на **частоте инцидентов**, а не в горячих путях (§3, цель «быстрее»).

## 2. Целевая архитектура (4 слоя)

```
        ┌─────────────────────────────────────────────────────────┐
        │  LivingWorld.Core  — ЛЕДЖЕР = ЕДИНСТВЕННЫЙ АВТОРИТЕТ      │
        │  (чистый, тестируемый: население, фракции, дрифтеры,      │
        │   армии, экономика, вымирание — уже есть)                 │
        └───────▲───────────────────────────────────────▲──────────┘
                │ inbound: факты судьбы            outbound: запросы на
                │ (смерть/плен/возврат)            материализацию (рейд/приток)
        ┌───────┴──────────┐               ┌────────────┴─────────────┐
        │  SYNC-СЛОЙ        │               │  STORYTELLER/INCIDENT-СЛОЙ│
        │  (map → ledger)   │               │  (ledger → map)           │
        │  один адаптер,    │               │  свои IncidentDef +       │
        │  на IDENTITY-MAP, │               │  IncidentWorker, gated    │
        │  не на hot path   │               │  через ledger; пейсинг    │
        └───────▲──────────┘               │  через StorytellerComp/   │
                │                           │  категорию+MTB            │
                │                           └────────────┬──────────────┘
                └──────────────┬─────────────────────────┘
                     ┌─────────┴──────────┐
                     │  IDENTITY-MAP       │  ← спинной хребет:
                     │  ThingComp на пешке │    EntityId ↔ пешка,
                     │  ↔ EntityId ledger  │    переживает save/GC
                     └────────────────────┘
```

**Принцип нормализации:** ровно одна точка на каждое направление, все — на общей
идентичности; ваниль **не патчим на генерацию**, а **дополняем своим контентом** и
лишь **приглушаем** ванильные людские угрозы.

## 3. Спинной хребет: контракт идентичности (приоритет №1, §A)

Всё остальное держится на этом. `thingIDNumber` не годится — при GC пешки и
переспавне он протухает.

**Решение: свой `ThingComp` на пешке — `CompLivingWorldIdentity`**, несущий
`EntityId` ledger-записи. Свойства:

- **Переживает save/load** — `ThingComp.PostExposeData` сериализует `EntityId`
  вместе с пешкой (нативно).
- **Путешествует с пешкой** — при уходе в `WorldPawns`, караван, плен comp остаётся
  на объекте; не зависит от `thingIDNumber`.
- **GC-безопасно по замыслу:** если RimWorld собрал пешку — не важно, ledger —
  источник истины; при повторной материализации comp вешается заново из ledger.
- **Двунаправленный поиск:** прямой (пешка→EntityId — читаем comp); обратный
  (EntityId→активная пешка) — лёгкий рантайм-словарь `GameComponent`, строящийся
  при спавне/загрузке, а не персистентный (переживать ему нечего).

Comp вешается **на материализации** (§4) — единственном месте, где ledger рождает
пешку, — поэтому идентичность есть у 100% наших пешек с момента появления.

Для пешек, пришедших **не от нас** (ванильный wanderer, которого мы решили
«записать» — см. шаг 5 §4.2 «всегда записывать»), comp вешается в момент
inbound-захвата: создаём ledger-запись и тут же ставим comp.

> Замена `RaidPawnLink`-привязки по `thingIDNumber` на `CompLivingWorldIdentity`
> — отдельный самостоятельный срез (обратно совместимый: старые сейвы без comp'а
> откатываются на thingIDNumber, новые — на comp).

## 4. Outbound-слой: свои инциденты вместо патчей генерации

### 4.1 Базовый механизм RimWorld (нативный)

Сторителлер собирается из `StorytellerComp`, каждый тянет инциденты **по
категории** (`IncidentCategoryDef`: `ThreatBig`, `AllyArrival`, `Misc`, …) с
пейсингом (`CompProperties_...MTB`/`OnDays`). `IncidentDef` объявляет
`workerClass : IncidentWorker`, `category`, `targetTags`. `IncidentWorker`
переопределяет `CanFireNowSub(IncidentParms)` (гейт — «есть ли чем наполнить из
ledger?») и `TryExecuteWorker(IncidentParms)` (материализация из ledger).
→ verify против `Assembly-CSharp.dll` при смене версии игры.

### 4.2 Два уровня контроля пейсинга (из §3, аддитивно → опционально)

- **Уровень 1 (рекомендуется первым): свой `IncidentDef` в ванильной категории.**
  Никакого своего сторителлера. Наш `LivingWorld_FactionRaid` (категория
  `ThreatBig`) и `LivingWorld_DrifterArrival` (`AllyArrival`) кладём в общий пул —
  **ванильный сторителлер сам планирует их** по своим MTB/весам. Частоту
  регулируем весом инцидента + гейтом `CanFireNowSub` (нет населения/дефицита —
  инцидент не может выстрелить). Максимально совместимо (Cassandra/Randy/любой мод).
- **Уровень 2 (опционально): свой `StorytellerComp`**, подмешиваемый во все
  `StorytellerDef` через `PatchOperationAdd` на `<comps>`. Даёт свои MTB-кривые,
  завязанные на **дефицит ledger'а** (гомеостаз §5): мир опустел → чаще, здоров →
  реже. Это нативная реализация «кран регулирует частоту», которой не хватало.
- **Уровень 3 (opt-in): свой `Storyteller` «Живой мир»** — отдельный выбор, полный
  ledger-темп. За рамками нормализации, отдельный трек.

### 4.3 Приглушение ванили (не вырезание)

Чтобы не было «двойных» людских рейдов, ванильные людские угрозы **ослабляем**, а
не убираем (§E: аддитивность, не спорить с рассказчиком):

- Предпочтительно — **XML `PatchOperation`** на вес/частоту ванильных
  human-raid инцидентов (данные, не код; совместимо, откатываемо).
- Минимальный Harmony-`CanFireNowSub`-гейт на ванильном human-raid — **только**
  если XML недостаточно; это единственный допустимый остаточный outbound-патч, и
  он **гейт**, а не переписывание генерации (на порядок меньше поверхности, чем
  текущие `TryResolveRaidFaction`/`TryGenerateRaidInfo`).
- Не-людские угрозы (мехи/жуки/сущности) — не трогаем вообще (humanlike-гейт, §2).

### 4.4 Что куда переезжает

| Механика | Сейчас | Нормализовано |
|---|---|---|
| Рейд людьми из ledger | patch `TryResolveRaidFaction` + `TryGenerateRaidInfo` | `IncidentDef LivingWorld_FactionRaid` (ThreatBig) + `IncidentWorker_LivingWorldRaid`, тянет армию/пешек из ledger; ваниль-human приглушена |
| Приток дрифтеров (шаг 5 Part B) | *(план)* patch `WandererJoin` | `IncidentDef LivingWorld_DrifterArrival` (AllyArrival) + worker; gated дефицитом; «всегда записывать» через тот же путь |
| Беженцы/поды (позже) | — | новые `IncidentDef` в тех же категориях, тот же worker-паттерн |

`VanillaRaidInterceptor`/`RaidReconciliationService` (чистая Core-логика) —
**переиспользуются как есть**; меняется только точка входа (свой worker вместо
патча ванили).

## 5. Inbound-слой: один sync-адаптер на идентичности

Судьбы активной карты (смерть/плен/уход) обязаны возвращаться в ledger — это
остаётся (§3: «не отменяет обратный sync»). Но нормализуем:

1. **Единая точка входа.** Вместо 4 разрозненных патчей — один сервис
   `LivingWorldPawnSyncService` (Core, тестируемый), принимающий факт
   `(EntityId, FateKind, tick)`. Тонкие адаптеры лишь ловят событие и резолвят
   `EntityId` через `CompLivingWorldIdentity` (§3), а не по `thingIDNumber`.
2. **Уход с горячего пути.** `Pawn.DeSpawn` (горячий) заменяем на менее частые
   сигналы: `Pawn.Kill` (смерть — редко), `Pawn_GuestTracker.CapturedBy` (плен —
   редко), а «покинул карту живым» ловим по `Pawn.ExitMap` (уход каравана/побег —
   редко) **без** `DeSpawn`. Если какой-то переход ловится только на `DeSpawn` —
   ставим **gated-префикс**, срабатывающий лишь для пешек с нашим comp'ом (99%
   деспавнов — колонисты/животные без comp'а — выходят мгновенно).
3. **Обратный sync вербовки/эмансипации (§2.A, пробел).** Добавляем хуки на
   рекрут/порабощение/эмансипацию пленника, чтобы ledger знал, что пленник сменил
   фракцию/вернулся к своим (закрывает §9-хук). Тоже через identity-comp.

## 6. Производительность (gap-analysis §1, §2.C)

Нормализация **сама по себе** снимает главный перф-риск: логика населения уходит на
**частоту инцидентов** (редко, по MTB), а не в per-tick/per-despawn. Дополнительно:

- **Никакого per-citizen LINQ в горячих путях.** `CanFireNowSub` должен читать
  **кэш-агрегаты** (дефицит популяции, сила фракций), а не гонять `state.Citizens`
  каждую проверку. Кэш пересчитывается в дневном тике (§time-dilation), не в гейте.
- **Не плодить world pawns.** Материализуем только то, что реально видит игрок
  (рейд/приход на карту); остальное живёт как компактная ledger-запись → мы
  **уменьшаем** WorldPawns-блоат, а не добавляем (совместимость с RuntimeGC/RocketMan).
- **Дневной world-tick — планировщик**, не пер-сущностный проход (уже так для
  экономики/миграции; drifter-конвейер шага 5 Part A встраивается туда же).

## 7. Совместимость (§D — это личный модлист проекта)

- **Rim War (приоритет №1):** свой инцидент **резко снижает** конфликт — мы больше
  не патчим ту же ванильную генерацию, где сидит Rim War. Остаётся адаптер «не
  дублировать людские угрозы, если Rim War уже ведёт эту фракцию» — но это теперь
  **гейт в нашем `CanFireNowSub`**, а не война за один Harmony-метод.
- **Несколько модов патчат генерацию рейдов (§D):** уходя со своего патча
  генерации, мы вычёркиваем себя из этой свалки; тест «не ломаемся, если рейд уже
  перехвачен» становится тривиальным (мы не перехватываем).
- **DLC-гейтинг (§B):** воркеры деградируют fail-open без Ideology/Biotech/др.

## 8. Карта миграции (инкрементально, тесты зелёные на каждом шаге)

Порядок — от хребта к листьям, каждый шаг самодостаточен и покрыт TDD:

1. **Identity-comp (§3)** — `CompLivingWorldIdentity` + обратный словарь;
   материализация вешает comp; sync резолвит по comp с fallback на thingIDNumber.
   *(Разблокирует всё остальное; обратно совместимо.)*
2. **Свой drifter-arrival инцидент (§4.4)** — заменяет Part B шага 5 (postfix
   `WandererJoin`) на `IncidentDef + worker`, gated дефицитом. *(Шаг 5 Part A —
   дневной конвейер — не затрагивается, идёт своим чередом.)*
3. **Свой faction-raid инцидент (§4.4)** — переносит `VanillaRaidInterceptor`
   на свой worker; приглушение ванили через XML-patch (§4.3); **снимаем** патчи
   `TryResolveRaidFaction`/`TryGenerateRaidInfo`.
4. **Консолидация inbound (§5)** — `LivingWorldPawnSyncService` + увод с
   `Pawn.DeSpawn`; добавить sync вербовки/эмансипации.
5. **(опц.) `StorytellerComp` уровня 2 (§4.2)** — гомеостатический пейсинг по
   дефициту ledger'а.

## 9. Открытые вопросы

- **Приглушение ванильных human-raid: XML-patch веса vs минимальный `CanFireNowSub`-гейт?**
  Нужен замер, достаточно ли данных-патча (предпочтительно), или требуется гейт.
- **`StorytellerComp` уровня 2: подмешивать во все `StorytellerDef` или только в
  свой рассказчик?** Подмешивание меняет поведение чужих рассказчиков (аккуратно с
  ожиданиями игрока, §E).
- **Материализация рейда: сколько пешек реально спавнить** при большой ledger-армии
  (points-кривая ≠ число пешек, §1) — переиспользуем reconciliation, но точку
  спавна в своём worker'е надо провалидировать.
- **Identity-comp на не-наших пешках:** вешать на всех «записанных» приходах, или
  только на тех, чью судьбу трекаем? (Влияет на объём обратного словаря.)

## 10. Влияние на уже написанную спеку шага 5

- **Part A (дневной конвейер в тике)** — **без изменений**, встраивается как и
  спланировано (это планировщик, не патч).
- **Part B (материализация притока)** — **меняется точка входа**: вместо Harmony
  `Postfix` на `IncidentWorker_WandererJoin` — свой `IncidentDef
  LivingWorld_DrifterArrival` + `IncidentWorker` (§4.4, шаг 2 миграции). Семантика
  «всегда записывать» и Core-методы (`MaterializeDrifter`/`MaterializeNewArrival`,
  событие `DrifterMaterialized`) сохраняются — меняется лишь адаптер, который их
  вызывает, и он теперь вешает `CompLivingWorldIdentity`.

Спеку шага 5 нужно обновить под это (или вынести Part B в отдельный срез «свой
drifter-инцидент», следующий сразу за identity-comp).
